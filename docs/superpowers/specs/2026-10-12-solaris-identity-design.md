# Solaris-ui — sub-project 1: Identity (rename and theme)

Date: 2026-10-12 · Status: pending written review · Program: `2026-10-12-solaris-program-design.md`

## Goal

When this sub-project is done:

- Nothing in the repository is called Glowup. The library is `@its/solaris-ui`, the site is
  "Solaris", and the docs deploy to `https://itsolutions-dev.github.io/Solaris-ui/`.
- `createTheme()` returns the organization's theme, corrected, and every component renders
  with it.
- The theming page shows the organization's tokens and a gallery of real components that
  re-render when light and dark are switched.
- Components still have Glowup's prop names. Those change in sub-project 2.
- Nothing is published to npm.

## Part B — Theme

### Input: `createTheme(options?)`

MUI v6's own `colorSchemes` shape, a subset of it:

```ts
interface PaletteColorOptions { main: string; contrastText?: string }

interface PaletteOptions {
  primary?: PaletteColorOptions;
  secondary?: PaletteColorOptions;
  error?: PaletteColorOptions;
  warning?: PaletteColorOptions;
  info?: PaletteColorOptions;
  success?: PaletteColorOptions;
  background?: { default?: string; paper?: string };
  text?: { primary?: string; secondary?: string };
  divider?: string;
}

interface ThemeOptions {
  colorSchemes?: { light?: { palette?: PaletteOptions }; dark?: { palette?: PaletteOptions } };
  typography?: { fontFamily?: string };
}

createTheme(options?: ThemeOptions): Theme   // options deep-merged over the default
<ThemeProvider theme={theme}>                // `theme` optional; defaults to createTheme()
```

`ThemeProvider` keeps its current behaviour: it follows the OS colour scheme, and
`toggleTheme()` overrides it.

Removed from the public API: `palettes`, `createPalette`, `ThemePalette`, `PaletteId`,
`PaletteChroma`, `BASELINE_SEED`, `initialPalette`, `palette` and `setPalette`.
`providers/successRoles.ts` is removed, and its roles move into the theme. `providers/tonal.ts`
stays internal and does the derivation.

### Default theme (`providers/theme.json`)

`theme.json` keeps `typography`, `spacing` and `shape`. Its `colors` block is replaced by the
organization's input:

| | light | dark |
|---|---|---|
| `primary.main` | `#1D5B9D` | `#5893D4` |
| `secondary.main` | `#61B340` | `#61B340` |
| `background.default` / `paper` | `#F0F2F5` / `#FFFFFF` | `#111111` / `#171717` |
| `text.secondary` | `#64748B` | derived |
| `divider` | `rgba(0, 0, 0, 0.12)` | `rgba(255, 255, 255, 0.12)` |
| `error` / `warning` / `info` / `success` | MUI defaults `#d32f2f` / `#ed6c02` / `#0288d1` / `#2e7d32` | MUI defaults `#f44336` / `#ffa726` / `#29b6f6` / `#66bb6a` |

The colour types are no longer derived from the JSON, so the `_ThemeTokensInSync` guard keeps
only its typography, spacing and shape checks. The derivation is typed to return
`ThemeColorTokens`, so the compiler still catches a missing role.

### Derivation: input → Material 3 roles (`theme.colors`)

For each of the six colours X (`primary`, `secondary`, `error`, `warning`, `info`, `success`)
in each scheme:

- **`X` = `main`, exactly as given.**
- **`onX`** = `contrastText` if given. Otherwise `#FFFFFF` or `#000000`, whichever contrasts
  more with `main`. The better of the two is always at least 4.58:1 (√21), so AA holds for any
  `main`. A fixed choice does not: on MUI's info blue `#0288d1` white gives only 3.86:1, while
  black gives 5.44:1.
- **`XContainer` / `onXContainer`**: a tonal palette of `main`'s hue at chroma 48 (today's
  TonalSpot primary value). Light uses tones 90 / 10, dark uses tones 30 / 90.
- **`inversePrimary`**: tone 80 (light) or tone 40 (dark) of the primary palette.

Neutrals:

- `background` = `background.default`, and `surface` = `background.paper`.
- `onBackground` and `onSurface` = `text.primary` if given, else neutral tone 10 (light) or 90
  (dark).
- `onSurfaceVariant` = `text.secondary` if given, else neutral-variant tone 30 (light) or 80
  (dark).
- `outlineVariant` = `divider` if given, else neutral-variant tone 80 (light) or 30 (dark).
- Every other surface, inverse, outline and tertiary role is derived exactly as
  `createPalette` derives it today, from the primary hue.

`ThemeColorTokens` gains `success`, `onSuccess`, `successContainer`, `onSuccessContainer`, and
the same four for `warning` and `info`. `Button` (its `tone`) and `StatusBadge` read these
roles instead of the fixed ones in `successRoles.ts`.

### Read side: `theme.palette` (MUI shape)

`useTheme().theme` gains `palette`, resolved for the current scheme:

- `palette.mode`
- For each of the six colours: `palette.X` = `{ main, light, dark, contrastText }`.
  - `light` and `dark` use MUI's own algorithm: lighten by 0.2 and darken by 0.3.
  - `contrastText` = `onX`.
- `palette.background` = `{ default, paper }`.
- `palette.text` = `{ primary, secondary, disabled }`. `disabled` is `onSurface` at 38% alpha.
- `palette.divider`.

`theme.colors` (the Material 3 roles), `typography`, `spacing`, `shape` and `isDark` are
unchanged. These are the fields DBE-CRM actually reads (`primary.main` 95×, `error.main` 35×,
`text.secondary` 21×, `*.light` 18× and so on). `palette.action.*` (4 uses) is left out until
something needs it.

### Selection states follow primary

`secondary` is now the brand green, so the 14 components that draw selection and tonal states
from `secondaryContainer` / `onSecondaryContainer` / `secondary` switch to the primary
equivalents. Otherwise navigation indicators, selected chips, tonal buttons and similar
states would turn green.

The 14 components: Banner, Button, Chip, ClockPicker, IconButton, ListItem, Modal,
NavigationBar, NavigationDrawer, NavigationRail, CircularProgress, Snackbar, Tabs and
ToggleButton.

This matches DBE-CRM's `activePill`: a light primary tint behind the active tab.

### Shape

- `shape.extraLarge`: 28 → **24**, so dialogs and sheets use 24.
- A new `shape.full` (9999).
- Button and the button family (ButtonGroup outer corners, SplitButton, ProgressButton,
  ToggleButton) → `full`.
- Card: `medium` → `large` (16).
- Input (12) and Paper (16) already match.

### Font

DBE-CRM's stack `Roboto, Inter, sans-serif` becomes one family per platform, because React
Native has no font fallback and iOS **raises an error for an unregistered family**. The
default `typography.fontFamily`:

- **Android**: `"Roboto"`, which is the system font.
- **Web**: `"Roboto, system-ui, sans-serif"`. Web allows stacks. The docs site loads Roboto
  400, 500 and 700 in `app/+html.tsx`.
- **iOS**: `"System"`. An app that embeds Roboto (the expo-font config plugin, which needs a
  development build) opts in with `createTheme({ typography: { fontFamily: "Roboto" } })`. The
  getting-started page documents this.

### Corrections that land in later sub-projects

Custom tokens arrive together with the component that first uses them, not before:

- **The brand gradient** (one blue, `#1D5B9D`) and its grey disabled variant arrive in 3a,
  with `Button variant="gradient"` and the Drawer's selected item.
- **`tint()` and `colorFromString()`** arrive in 3a, with `Chip` / `Avatar` `color`. They fix
  the dark-pastel bug, the dead dark-mode lightness code and the `NaN` on non-hex input, and
  they drop the three near-white pastels.
- **`iconTile`** (90 / 16) arrives in 3b, with `IconTile` and `BigButton`.
- **The header radius** (24) and **the active pill** arrive with `AppBar` `rounded` in 3a and

- **Dropped:** `mutedColor` (`#94a3b8`, only 2.6:1 on white) is replaced by `text.secondary`.
  `greys.*` maps to `text.*` and `divider`. `white` and `phoneMaxWidth` are dropped.
- `greys.dark` (undefined in DBE-CRM) and `graphs.*` stay in the app. The chart palette comes
  in 3c.
